# cfr-inputs

Generates the inputs of the six-layer CFR pegging policy (issue #203): a
fixed pegging policy, solved with CFR+, that the play-table measurement uses
for every real choice either player makes during the play.

## What it generates

- **menus:** for each of the 3,640 pairs of four-card hand and seat, every
  point in pegging where that player has a real choice of card, as the player
  sees it (own hand plus the cards played so far). These are the decisions
  the policy has to make.
- **trees:** for each of the 1,820 Pone hands, every way the pegging can go
  against every possible Dealer hand, with the final pegging margin at each
  leaf.
- **offsets:** where each menu's probabilities start in the one flat policy
  array.
- **the CFR+ mixture policy and its exact certificate.**
- **the counterfactual support bits.**

**Why 1,820 and 3,640.** Hands are rank-only: nothing in the play scores by
suit, so suits are dropped. A four-card hand is then a multiset of ranks,
because ranks can repeat (5-5-J-K). The number of multisets of size k drawn
from n kinds is C(n + k - 1, k), so there are C(13 + 4 - 1, 4) = C(16, 4) =
1,820 hands. (C(13, 4) = 715 would count only hands with four different
ranks.) No rank can appear more than four times in four cards, so every one
of them can be dealt. Each hand can be held by Pone or by Dealer, which gives
3,640 hand-and-seat pairs.

**The six layers.** The policy makes every real choice in the hand: each
seat's first three cards, wherever more than one rank is legal. Two seats
times three cards are the six layers; a seat's fourth card is always forced.

**The legacy heuristic.** Wherever the move is forced (one legal rank, a go, or
a player's last card), the generator plays the legacy pegging heuristic, the
rule-based policy in `artifact_pipeline/pegging.py`. Any rule plays the same
card there, so the heuristic's rules change no game value. Each menu record also
stores the heuristic's choice at that decision, for consumers that want to
compare the policy with it. Nothing in this package reads that byte back, and
the play-table measurement (#238) computes the heuristic's choice in Python
itself. Because the stored choice is part of the menu files, the heuristic's
tie-break order is part of the generated bytes.

## Why the output is correct

Each part of the evidence lives in this repository:

- **The pegging rules** (`game.rs`): unit tests whose expected values are
  worked out by hand from the cribbage rules, one per scoring case and one
  per heuristic rule, in priority order.
- **Menus and trees** (`menus.rs`, `trees.rs`): menu records are checked for
  order and parent links, and the builder asserts perfect recall (the same
  public history always implies the same earlier own decision and the same
  legal ranks). A tree survives a round trip through its file format, and the
  heuristic's path through it reaches the same margin as replaying the hand
  from the rules. The binary's subcommands, exit codes and argument errors
  are tested on output folders small enough for a test.
- **Solve** (`solve.rs`, `driver.rs`): the solver's certificate computes, in
  exact `i128` arithmetic, each player's best-response value against the
  rounded policy. Its exposure is half the gap between them, the average of
  the two players' possible gains from deviating. The solve stops only when
  exposure is at most 0.001 points, so neither player could gain more than
  0.002 points. On a small game, tests check the certificate's joint value
  against a replay of every deal from the rules, and both best responses
  against an expectimax replay; neither replay reads the trees, so they also
  check the trees' values. Other tests cover the rounding, falling exposure,
  the iteration cap, the certificate schedule, and pause, crash and resume
  behaviour, including damaged or mismatched saved state.
- **Support** (`support.rs`): on a small game, the support bits are checked
  against a replay of each policy that walks every deal from the rules and
  never reads the trees.
- **Determinism:** the numerical outputs (regrets, averages and so the policy)
  do not depend on the thread count (`bytes_do_not_depend_on_thread_count`);
  only the measured seconds in certificates and `curve.jsonl` vary between runs.
  And a pinned digest of a small game's arithmetic flags order changes that
  alter that game's results. Menus, trees and offsets depend on no prior: they
  are fixed by the pegging rules, the heuristic's stored choice, the canonical
  hand order and the file format. Their digests are in `digests.json` under
  `reproducible`, and every build of this source must reproduce them.

The generator arrived in stacked pull requests: the pegging rules, then
menus, trees and offsets, then the solve, then these support bits.

## Why Rust

- **Throughput:** native code with no runtime or garbage collector, so more
  simulation fits in the same time, which tightens error bounds.
- **Safe parallelism:** the compiler rules out data races, `unsafe` is
  forbidden here, and rayon spreads the work across cores while the output
  bytes stay the same for any thread count. Joint discard-and-pegging
  solving, score-aware play and longer runs all need far more compute than
  this policy, so that headroom matters.
- **A successor to C++:** comparable speed and control, with memory safety
  checked at compile time.

## Port history

The method was first developed as unpublished research code in C++. This package
is a port of it. On full-size runs it reproduced that implementation's menus,
trees and offsets byte for byte; given the research prior, its policy; and given
the research policies and priors, its support file, and every integer in its
certificates (their display-only exposure value and timing can differ). Two
separately written implementations agreeing exactly is extra evidence, but
nothing here depends on the research code: every input the project ships is
generated from this repository's source. The solver adds its floating-point
terms in the same order as the research code, with no fused multiply-add, which
is what made the byte comparison possible. That order may change in future, but
a change can alter the low bits of the policy, so it needs the full-size check,
and a re-pin and fresh certificates if the bytes change.

## What each module does

| Module | Output |
|---|---|
| `game.rs` | rank-only pegging rules and the legacy heuristic |
| `menus.rs` | `menus/{k}.bin`, 3,640 files |
| `trees.rs` | `trees/{p}.bin`, 1,820 files; `offsets.bin` |
| `solve.rs` | the CFR+ iteration, the rounded policy, the exact `i128` certificate |
| `driver.rs` | checkpoints, `policy-N.bin`, `certificate-N.json`, `policy.bin` |
| `support.rs` | `support.bin` |

The solve driver's behaviour:

- **Pausing never certifies.** Certificates come only at iterations 1, 8,
  32 and every multiple of 128, so a resumed solve ends on the same policy
  as an uninterrupted one.
- **A crash during certification is repaired.** A resume first certifies a
  scheduled checkpoint that has no certificate yet.
- **A finished solve is never continued.** Running `solve` again returns the
  recorded result.
- **Resume checks the saved state.** It verifies the checkpoint's SHA-256
  digests and the inputs' identity: the prior plus the menu and tree
  digests. Files are flushed to disk before each rename.

## Parallelism without changing bytes

Every floating-point accumulator receives its terms in the serial order,
whatever the thread count.

- **Pone's pass** runs Pone hands in parallel.
- **Dealer's pass** keeps Pone hands sequential and runs Dealer hands in
  parallel.
- **Per-menu updates** run per file.

`solve.rs` explains why each choice preserves the order.

## Usage

```sh
cargo build --release
B=target/release/cfr-inputs
$B menus   --output OUT [--range START..END]
$B offsets --output OUT
$B trees   --output OUT [--range START..END]
$B solve   --output OUT --prior PRIOR.bin [--pause-after-seconds S]
$B support --output OUT (--policy POLICY.bin --prior PRIOR.bin)...
$B digests --output OUT
```

`--range` writes only those menu files (0..3640) or tree files (0..1820),
so the work can be split across jobs. `trees` needs every menu file.

`solve` exits with:
- 0 when the 0.001-point exposure target is met;
- 3 when it pauses on its time budget (run the same command again to
  resume);
- 4 at the iteration cap.

`support` sets one bit per `--policy`/`--prior` pair, in the order given:
bit `k` of a menu's byte says whether the opponent, following policy `k`,
reaches that decision with positive weight under prior `k`. The shipped
chain passes one pair, the solved policy with the prior it was solved on.

`digests` prints the SHA-256 of each output. For the menu and tree folders it
prints the SHA-256 of the per-file digests, one per line in file order. The
printed values can be compared with `digests.json`.

## Evidence

Measured on an Apple M2 with 8 threads, 2026-11-10, with binary sha256
`42160cc1...` built from the top of this stack of pull requests:

| Step | Time | Notes |
|---|---|---|
| menus | 60 s | matched the `reproducible` digest |
| trees | 73 s | matched the `reproducible` digest |
| solve | 32 to 34 min uninterrupted | 3.7 to 4.1 GB peak RSS; converged at iteration 128 |
| support | 14 s | |

The run paused the solve at iteration 31 with `--pause-after-seconds 600`
(exit 3), then resumed with the same command and converged at 128, ending
on the same policy as uninterrupted runs. As port evidence (see Port
history), on the research prior the solve also reproduced the research
policy and the integers of its certificates byte for byte, and `support`,
given the research policies and priors, reproduced the research two-bit
support file; those digests are under `port_evidence` in `digests.json`.
